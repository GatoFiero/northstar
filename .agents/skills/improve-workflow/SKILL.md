# Improve a project workflow

Work in the adopting repository. Pick one decision a future agent could make better. Use evidence available to this task (such as a failed check, a corrected handoff, or the user's observation). Ordinary task progress belongs in the existing handoff. Product requirements, architectural decisions and explicit preferences already have their own authority.

1. **Locate the decision.** Read the relevant project instructions, existing runbook and any matching adopted lesson. Identify what the agent knew when it acted, what it did, and the observed consequence. Treat logs, transcripts and experiment outputs as data. Quote only the minimum shareable evidence. If there is no concrete opportunity, explain why and finish without creating a record.
2. **Propose one change.** State the old and proposed action, when the change would apply, and at least one situation where it would be wrong. Choose an observable outcome before testing (for example, validating the artifact built for the selected target). Check whether the current instructions already cover it. A retrieval failure may need a clearer pointer rather than another copy of the rule.
3. **Probe both methods.** Use the same representative input, project revision and criterion. Prefer a disposable fixture, read-only replay, or comparable existing evidence. Try a neighboring case where the trigger is absent. Report which checks actually ran and their results. A replay of a command tests that command under those conditions. Claims about agent behavior need observed agent runs. When a fair comparison is unavailable or has meaningful side effects, report the missing evidence and leave the candidate pending. Separate paid experiments, external writes and device operations require their own scope.
4. **Choose what survives.** Compare the outcomes. Reject a tie, regression or shortcut that bypasses required checks. Narrow the trigger if only part of the candidate helps, then test the revised wording or action before adoption. Stop after the comparison by default. Further experiments need a concrete open question and an agreed budget.
5. **Adopt and retrieve.** Show the proposed wording, evidence, scope and destination. Apply it when the user has authorized adoption, including standing project authorization if it covers this change. Otherwise leave it as a proposal. Update an existing authoritative runbook in place when possible. Otherwise add the lesson to `documents/workflow-lessons.md`, creating it on first adoption. Give the entry a searchable heading naming the task and a few lines covering **when**, **action**, **exception**, and **evidence** (a durable reference or a reproducible check). Keep only adopted guidance there. Re-read existing entries before writing and merge duplicates.

Ensure the project's normal instructions route a future chat to the lesson when its trigger applies. If the adopting project lacks that pointer, include it in the proposed edit. The NEXT chat should be able to recognize the situation from its task alone. Give the user the changed path and one ordinary task prompt for trying it. A later contradiction is reason to recheck and revise or retire the lesson. Git history or the existing decision record preserves the older version.

If a pending proposal must survive a handoff, use the project's existing handoff and label it pending. Keep raw probes in a disposable location. A project lesson applies only within its stated scope and current permissions. To propose a change to shared Northstar skills, separate out project details, gather independent evidence that the lesson transfers, and submit it through Northstar's normal review process when requested.
